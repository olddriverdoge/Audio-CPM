# 工作模式采样说明（简版，约两千字）

工作模式采样，指把 Audio-CPM 的三档音频输出路径放在同一套素材、同一套指标下逐档运行并横向对比。它是验证方法，不是新功能：证明每一档真的跑在预期路径上，量化三档在延迟、断续与音质上的差别，并把"面板显示在播、实际早已降级"这类隐性错误变成可判定的失败。三档的差别不在解码，而在最后一公里的写入方式与缓冲策略。

三档不是并列配置，而是一条单向回退链：先要独占，拿不到才退共享，共享也失败才退默认 sink。模式字段的推导只有一行——活动且独占报 `aaudio_exclusive`，活动但非独占报 `aaudio_shared`，不活动报 `shared`。这行必须与 `active`、`exclusive`、`fallback`、`error` 四个字段互相印证；四者各自为政是最常见的漏检点，比如 `active=true` 同时 `fallback=true` 这种自相矛盾的状态。

独占模式 `aaudio_exclusive` 走 AAudio 独占流，性能模式固定 LOW_LATENCY。缓冲目标取 `sampleRate/12`，约合 80 毫秒，容量按目标的两倍申请，打开之后再调用一次 `setBufferSizeInFrames` 兜底。这一步不可省：部分 ROM 的 builder 只认容量上限，不会自动把实际可写空间提到目标值，省掉就会出现"标称 80 毫秒、实际只有几毫秒"的假缓冲。

打开成功不等于参数正确。必须回读实际采样率、声道数与格式，逐项与请求比对，任一不一致立即关闭该流并置错误 `AAudio actual mismatch`。这个闸门防的是最隐蔽的一类错误：以为拿到了 48k 独占流，实际是 44.1k 共享流，面板数字好看，音质与时钟漂移却已经错位。

`aaudio_shared` 是独占失败后的第一次自动重试，由 cpp 侧完成。流程是先试 EXCLUSIVE，失败后打印一行独占不可用、重试共享，再按 SHARED 打开一次。它仍然是 AAudio 原生流，PCM 依旧经 `nativeWrite` 写入硬件队列，只是不再独占设备，要与系统混音共享同一路输出。

`shared` 是最后一级，走 Media3 的 DefaultAudioSink。进入这一级只有两类原因：AAudio 的独占与共享两级都打不开，或者前置条件根本不满足、连尝试都不该尝试。此时变速变调交给 Sonic 在默认 sink 内部完成，原生写路径完全不参与。

前置条件是白名单式的，全部满足才放行：SDK 26 及以上、声道数不超过 2、线性 PCM 且为 16 位整型或浮点、播放倍速与音调都等于 1.0、声道映射为直通、音频处理管线处于激活态、原生打开成功且实际参数与请求匹配。任何一条不满足都应直接走 fallback，而不是先开开看；硬开的结果通常是声道错位或持续 underrun。

"采样"有两层含义，测试中同时用到。一层是采样率桥接，模型侧 16k/24k 与硬件侧 44.1k/48k 之间的转换；另一层是在三档下采集同一段音频的运行数据做对比。分档采集必须控制变量：同一素材、同一音量、同一播放起点、同一统计窗口，三档各跑一遍，唯一变量只剩工作模式，比较才成立。

素材要覆盖典型频谱与边界情况：1k 与 4k 正弦查失真与频偏，20 到 20k 扫频查高频是否被抹糊，白噪声查混叠，语音查语速与清晰度，音乐查复杂频谱下的互调，静音段查底噪与随机突爆。六类各跑三档构成完整矩阵。

指标分三组。延迟看 `framesPerBuffer`、`latencyMs` 与播放位置推进：独占缓冲小、延迟低但更怕 underrun，共享缓冲由系统混音决定、通常更大更稳。断续看 xrun，cpp 已有 `nativeXRunCount` 直接读硬件计数，但 Java 侧的状态描述尚未带出，当前只能靠日志人工核对。音质沿用离线那套，回采后算信噪比、谐波失真、对数谱距离与直流偏移；某一档明显劣化，多半不是模式本身，而是中间又插了一次重采样。

系统二次转码要专门核对。做法是在同一时刻比三个采样率：设备原生率 `deviceSampleRate`、AAudio 实际流率 `aaudio.sampleRate`、源流率 `sourceFormat.sampleRate`。硬件率与流率不一致，说明系统在中间又转了一次，等于两级重采样串联，失真与延迟都会叠加。

还有三处缺口和一个风险。缺口是 xrun 未上报、缺真实发送计数、缺模式迁移事件——现在只有当前态快照，没有"何时、因何、从哪一档到哪一档"。风险是伪模式：只看 `playing` 为真就认为正常，实际可能早已掉到 fallback。因此采样必须三件套一起看：`mode`、`fallback`、`error`。

把这些写成门禁：三档模式与四个状态字段自洽；独占被拒必须先落共享、只有两级都失败才退 fallback；分档的延迟与 xrun 达到阈值；音质不劣于基线；切换无爆音且错误可归因。任何一条不满足即判失败，不改断言去迁就现状。

落地三步：先在真机按素材矩阵分档采集一轮人工数据，确认三档都能稳定复现；再补 xrun、发送计数、模式迁移三项埋点，把人工判断转成自动化断言；最后并入发版前必过项。本轮只交付说明文档，不动代码、不递增版本号；埋点落地属于代码改动，届时再递增版本、跑回归并构建交付。
